# Проектирование ORM и базы данных

## Предметная область

Система учитывает сотрудников предприятия, их подразделения и производственные задачи.
У задачи есть подразделение-владелец, постановщик, один ответственный исполнитель,
состояние kanban-доски, приоритет, плановый срок и факт подтвержденного выполнения.
Отдельные таблицы ролей и состояний позволяют единообразно использовать коды в будущем API.

Один ответственный на задачу — принятое допущение: ТЗ требует распределения задач между
сотрудниками, но не требует коллективного исполнения одной карточки. Коллективное
исполнение при необходимости потребует таблицы назначений и новой миграции.

## Связи

| Родитель | Потомок | Кратность | Правило удаления |
|---|---|---|---|
| departments | employees | 1 : 0..N | RESTRICT |
| departments | tasks | 1 : 0..N | RESTRICT |
| employees | employee_personal_data | 1 : 0..1 | CASCADE |
| employees | users | 1 : 0..1 | RESTRICT |
| employees | tasks.assignee_id | 1 : 0..N, исполнитель необязателен | RESTRICT |
| roles | users | 1 : 0..N | RESTRICT |
| users | tasks.created_by_id | 1 : 0..N | RESTRICT |
| users | tasks.completed_by_id | 1 : 0..N, подтверждение необязательно до выполнения | RESTRICT |
| task_statuses | tasks | 1 : 0..N | RESTRICT |
| tasks | task_status_history | 1 : 0..N | CASCADE |
| task_statuses | task_status_history.from/to_status_code | 1 : 0..N | RESTRICT |
| users | task_status_history.changed_by_id | 1 : 0..N | RESTRICT |

Каждый сотрудник обязательно состоит в одном подразделении. Отчество может отсутствовать.
Отсутствие личной карточки или учетной записи допустимо для черновика кадрового учета;
при наличии личной карточки все паспортные реквизиты, ИНН и СНИЛС обязательны.
Учетная запись связана ровно с одним сотрудником и ровно с одной ролью.
Руководитель подразделения определяется ролью `department_head` и подразделением
его сотрудника. Несколько руководителей в одном отделе не запрещены ТЗ.

Текущее подразделение сотрудника хранится в `employees.department_id`, подразделение
задачи — отдельно в `tasks.department_id`. При переводе сотрудника старые задачи сохраняют
подразделение-владельца. Проверку принадлежности сотрудника отделу **в момент назначения**
нужно выполнять будущим сервисом; постоянный составной FK на текущее подразделение
запретил бы перевод сотрудника с историческими задачами. Полной истории кадровых переводов
в этом этапе нет: отчет по численности отражает текущее распределение.

## Проверки уровня PostgreSQL

- PK — BIGINT GENERATED BY DEFAULT AS IDENTITY; справочники имеют строковые PK-коды.
- Внешние ключи не допускают ссылок на отсутствующие отделы, работников, пользователей
  и состояния.
- Уникальны код и название подразделения, ИНН, СНИЛС и пара серия/номер паспорта.
- Уникальность email и логина реализована индексами по `lower(...)`.
- CHECK запрещают пустые обязательные ФИО, заголовок, должность, телефон, логин и хеш.
- Серия паспорта — 4 цифры, номер — 6, ИНН — 12, СНИЛС — 11 без разделителей.
  Это строки, чтобы сохранять ведущие нули. Контрольные суммы — будущая валидация ввода.
- Email проверяется базовым CHECK формата; полная прикладная валидация появится со схемами API.
- Приоритет — 1–4. Срок и завершение не могут предшествовать созданию задачи.
- В состоянии `done` обязательны исполнитель, `completed_at`, `completed_by_id`.
  В остальных состояниях оба поля подтверждения должны быть NULL.
- История допускает NULL старого состояния только как незаданное начальное состояние;
  CHECK не позволяет записать переход состояния в то же состояние.

Подтверждение выполнения включает статус, дату, пользователя и запись истории в одной
транзакции. Таблица истории сейчас **не заполняется триггером или ORM-событием**:
демо-скрипт и тест делают это явно, а общий сервис изменения состояния относится
к следующему этапу. Допустимые переходы и права подтверждающего также будут проверяться
сервисом. БД обеспечивает структурную согласованность, но не исполняет ролевую политику.

## Жизненный цикл

Основные колонки: `new` → `in_progress` → `done`. `cancelled` добавлен как состояние
отмененной задачи, чтобы не смешивать отмену с выполнением. Правила возврата задачи
в работу будут определены в API. При возврате из `done` нужно одновременно очистить
оба поля подтверждения и сохранить событие истории.

`Task.is_overdue` — гибридное свойство: работает и как Python-атрибут, и как SQL-условие.
Просрочка означает `due_at < now` и состояние не `done`/`cancelled`; при отсутствии срока
просрочки нет. Завершение с опозданием определяется отдельно: `completed_at > due_at`.
Архивность — отдельный флаг представления доски и не меняет факт просрочки/выполнения.

Удаление подразделений и сотрудников со связями ограничено RESTRICT. Для сохранения
производственной отчетности предусмотрены `is_active` и `is_archived`; удаление новой
карточки без внешних ссылок возможно. При физическом удалении задачи ее история удаляется
каскадно. В будущем API удаление завершенных задач целесообразно заменить архивированием.

## Основа отчетности

Отчеты по фактическому выпуску используют `completed_at` и `assignee_id`, группируются
по месяцу/году и подразделению задачи. Для плановой исполнительской дисциплины предлагается
считать процент как число выполненных из задач со сроком в выбранном месяце / число
неотмененных задач со сроком в этом месяце × 100. При нулевом знаменателе показывать
«нет задач». Это проектное предложение, формула в ТЗ не задана.

Формирование отчетов и диаграмм в этом этапе не реализовано. Если потребуется неизменная
историческая аналитика по переназначению исполнителей и сроков, понадобится дополнительная
история назначений: текущая `task_status_history` отслеживает только состояния.

## Технические решения

Синхронный SQLAlchemy Session и psycopg 3 используются с обычными `def`-обработчиками
FastAPI. На запрос создается отдельная сессия, а транзакции в будущих сервисах будут
завершаться явным commit/rollback. Соединение открывается лениво, `pool_pre_ping` проверяет
его при получении из пула. Секретные параметры SQL не выводятся (`hide_parameters=True`).

`created_at` и `updated_at` — TIMESTAMP WITH TIME ZONE; приложение использует UTC.
`updated_at` обновляется механизмом SQLAlchemy `onupdate`, а не серверным триггером:
при ручном SQL его нужно устанавливать явно. Для ключей и ограничений задано единое
соглашение именования, чтобы последующие миграции были предсказуемыми.

Личные документы вынесены отдельно, чтобы их было проще исключать из будущих публичных
схем ответа. Само разделение таблиц не реализует защиту доступа или шифрование.

Физическая схема приведена в `erd.svg` и `erd.pdf`. Все поля и реальные ограничения
PostgreSQL перечислены в `data_dictionary.md`; они получены не вручную, а интроспекцией
БД после `alembic upgrade head`.
